# What's bridged

## Posts, replies, and threads

- **New posts**: a message in your linked Profile Room becomes an outgoing `Create{Note}`, addressed publicly and delivered to your followers' inboxes (plus anyone mentioned).
- **Incoming posts**: a followed account's `Create{Note}` is mirrored as a plain Matrix message into their Remote User Room. It's HTML-sanitized to a safe tag subset and deduplicated by the post's ActivityPub object ID.
- **Replies, both directions**: a Matrix reply or thread-reply to a mirrored post federates out with the correct `inReplyTo`, tagging the parent author and every other participant already in the thread (fetched live from the parent, so the "reply to @a @b" line reads correctly on the far end). Incoming replies are mirrored as real Matrix thread replies, walking up untracked ancestors and auto-importing the true root if needed so the reply always has somewhere real to land.
- **Guest posting**: a different local user posting inside someone else's Profile Room federates as their own post, under their own actor and outbox, with the room owner auto-mentioned.
- **Edits**: a Matrix edit (`m.replace`) federates as `Update` on the same Note ID, never delete-and-recreate, so replies, likes, and reposts referencing it stay intact.
- **Deletes**: redacting your own distributed post sends a signed `Delete` to every follower. An incoming `Delete` for a tracked post redacts the mirrored Matrix event, but only if the sender actually matches the recorded author.
- **Backfill**: `;backfill` (or an inbound reply chain with gaps) pulls an account's outbox or a specific thread's replies through the exact same mirroring path a live delivery uses, so history is indistinguishable from anything that arrived live.
- **Quote-posts**: Akkoma/Pleroma/Fedibird/Misskey-style quote fields are detected on the way in (any auto-appended "RT: link" fallback text is stripped) and rendered as a quote card. `;repost <caption>` sends a real quote-post of your own the other way.

## Reactions and reposts

- **Reactions**: a plain 👍 Matrix reaction sends `Like`. Any other emoji sends `EmojiReact` (a Pleroma/Misskey/Akkoma extension) carrying the literal emoji. Incoming `Like`/`EmojiReact` become `m.reaction` events from a ghost, and redacting a reaction in either direction sends or receives the matching `Undo`.
- **Reposts**: reacting with 🔁, or running bare `;repost` as a reply, sends a real `Announce` (not a Like) to both your followers and the original author, plus a "🔁 you reposted" card in your own Profile Room. An incoming `Announce` renders the same card and independently imports the reposted post into its original author's own room, so it's reply/react-able there too. Un-reposting (redacting the reaction, the command, or the card, all three are linked) sends `Undo(Announce)`.
- **Custom emoji**: Pleroma/Misskey/Akkoma image-emoji shortcodes (in post text, reactions, or display names) are resolved against the object's own metadata to an uploaded `mxc://` image and inlined next to the shortcode text, in both directions. Outgoing posts, replies, and edits written with a Matrix image pack (MSC2545 -- a `:shortcode:` typed with image-pack autocomplete turns into an `<img data-mx-emoticon>` in the message's `formatted_body`) carry a real AS2 `Emoji` tag pointing at the image, same as the inbound direction, so a remote Pleroma/Misskey/Akkoma viewer actually renders it instead of the bare `:shortcode:` fallback text. Reusing an emoji that was itself mirrored in from a remote instance keeps its original source identity rather than re-hosting a second copy under this bridge's own domain, since some implementations treat a re-hosted copy as an entirely different emoji from the original.
- **MSC4027 custom-image reactions**: reacting with a Matrix image pack (a custom-image reaction, animated GIFs included) always federates out as a custom-emoji `EmojiReact` with a real Emoji tag. The reverse -- mirroring an incoming custom-emoji reaction as an actual MSC4027 image reaction instead of `:shortcode:` text -- is opt-in (`bridge.msc4027_custom_reactions`, off by default, since it changes what non-MSC4027 clients render).

## Polls

- Polls are bridged bidirectionally, as real Matrix poll widgets (MSC3381), not text. A Profile Room poll becomes a `Create{Question}`; an incoming poll from a followed account is mirrored the same way a post is, but as an actual interactive poll.
- Voting either direction works: a local vote on a mirrored (remote-owned) poll federates out as a private vote to the poll's author; a remote vote on your own poll makes that voter's ghost cast a real Matrix poll response, so Matrix's own widget tallies it alongside everyone else's.
- A mirrored poll's results are shown as a "Fediverse Tallies" thread reply, seeded from whatever the poll already shows at import time and actively refreshed after a vote or via `;refresh poll` -- some remote servers (confirmed for Pleroma/Akkoma) never push a live tally update over federation at all, so this doesn't rely solely on one arriving.
- An incoming poll closing is mirrored as a real poll-end event in the same thread.

## Direct messages and chats

- **DMs** (`;dm`): a private, non-public `Create{Note}` addressed only to the recipient, in a dedicated ghost DM room. Threaded if replying within that same room.
- **Chats** (`;chat`): Pleroma/Akkoma's separate `ChatMessage` concept, in its own dedicated room type, flat with no threading. Also started by simply inviting a ghost into a fresh Matrix DM directly.
- Both directions mirror faithfully. An inbound private `Note`/`ChatMessage` lands in the matching room type, and a Matrix message sent there federates back out the same way.

## Mentions

- A Matrix client's structured mention (`m.mentions`) of a ghost or fellow local user is rewritten to `@user@domain` text and added as a real AS2 `Mention` tag on the way out. A hand-typed `@user@instance.org` is resolved the same way via WebFinger, and a ghost's or local user's full Matrix ID (`@localpart:server_name`) typed out by hand instead resolves the same way a real pill does (an exact repository lookup, not WebFinger).
- Incoming `Mention` tags are matched by handle, not raw URL since they routinely differ, against known ghosts/local users and rendered as genuine Matrix mention pills.

## Media

- Incoming attachments (image, video, audio, document) are downloaded and re-uploaded as real Matrix media. Extra attachments beyond the first are appended as links, since one ActivityPub post maps to exactly one Matrix event.
- Outgoing Matrix media becomes an ActivityPub `attachment` pointing at the bridge's own public media proxy (`/media/{server}/{id}`), never your homeserver directly, since remote servers have no Matrix access token. Only media explicitly published this way is ever served.

## Follows and moderation

- **Follows**: `;follow` sends a signed `Follow`. An incoming `Follow` is auto-accepted (or auto-rejected if the follower is blocked), recorded, and reflected as a ghost invite into your Profile Room, so room membership doubles as your visible follower list.
- **Unfollow**: leaving or being kicked from a Remote User Room sends a real `Undo(Follow)` under your own identity. An incoming `Undo(Follow)` just drops the follower record.
- **Block**: cuts any existing follow (a real `Undo(Follow)` if you were following them), kicks you from their rooms, declines future follows with a real `Reject`, and silences notifications, all in one command. An incoming `Block` surfaces as a notification and silently drops the follower record, since AP has no separate unfollow signal for a block.
- **Mute**: suppresses notifications and auto-invites from an account without touching the follow relationship or their content.
- **Followers/following visibility**: `;set hide_followers on`/`;set hide_following on` withholds just the member list of your public collections. Counts stay public either way, matching Mastodon's "hide network" convention.

## Per-identity settings

- **`;set`**: one mechanism for every per-ActivityPub-identity preference (`hide_followers`, `hide_following`, `discoverable`), replacing the old one-command-per-setting pattern. Run bare or as `;set list` to see them all. Scoped to whichever identity owns the current room, since a profile and any PeerTube channels it owns are each a separate identity with their own settings, and sparse: only an actual override from the code default is ever stored. For your main identity, it also works from inside your Fediverse Notifications room, a private place only you can see, so you don't have to manage your settings somewhere a Matrix-side follower in your Profile Room could see the traffic.

## Profile and identity

- Linking or creating a profile mints an ActivityPub `Actor` document with its own RSA keypair. Your room's name, topic, and avatar map to the actor's name, bio, and icon, pushed live as `Update` on every change.
- `;banner` sets the actor's header image via `m.room.banner` (MSC4221, currently under its own unstable prefix since Matrix has no stable room banner concept yet).
- MSC4501 discoverability: a linked Profile Room gets `m.social.profile_user_id` (asserting who it actually belongs to, since the bridge's bot is always its technical creator) with a power level requiring the room's owner to change it, and a ghost's Remote User Room gets `m.social.profile_room` (a `{room_id, via}` block) set on their own Matrix profile pointing back at it. Both stay in sync across a `;replace room`.
- An incoming profile change (`Update{Person}`) syncs the Remote User Room's name/avatar/banner and the ghost's own Matrix profile.
- `;replace room` recreates the Matrix room behind any identity (Profile Room, Remote User Room, DM, or Chat room) to pick up newer bridge features. It's entirely Matrix-side; nothing is sent over ActivityPub, since the identity itself doesn't change.
- `;delete profile` is a confirmation-gated, irreversible account deletion. It sends a signed `Delete` to every follower, then erases the local identity.

## Multi-identity support

Opt-in (`bridge.custom_identities_enabled`, off by default -- see [CONFIG.md](CONFIG.md#bridge-custom_identities_enabled)). With it off, the bridge behaves exactly as it always has: one ActivityPub identity per Matrix user, its username always the Matrix localpart.

- With it on, `;create profile <id>` (or `;link profile`, reattaching an existing room under a different identity) lets a Matrix user own several distinct ActivityPub identities at once, each with its own keypair and Profile Room, capped at `bridge.max_identities_per_user` (bridge admins exempt). The bare, no-`<id>` form of `;create profile` keeps deriving its username from your Matrix localpart no matter what, regardless of this setting.
- One identity is always your **Active** identity, used for anything that doesn't already have an identity implicitly tied to it: `;follow`, `;dm`, `;chat`, reacting/replying from a Remote User Room, and so on. `;id`/`;id list` shows your identities (numbered, Active one marked); `;id <number|id>` switches. You always have an Active identity once you have at least one -- deleting the Active one promotes another of your remaining identities automatically.
- Posting inside a specific Profile Room, or publishing to a PeerTube channel/Lemmy community already tied to one identity at creation, always acts as THAT identity instead of Active -- these were already implicit before multi-identity existed, and stay that way.
- Creating a new PeerTube channel or Lemmy community picks its owner the same way: automatically, if you only have one identity (unchanged, existing behavior), or via an explicit `as <number|id>` right after the channel/community's own `<id>` if you have more than one.
- A ghost DM or Chat room binds permanently to whichever identity started it, the moment it's first created -- switching Active afterward never changes which identity an existing conversation continues as, so a remote contact never sees a conversation suddenly switch "who" they're talking to.
- `;delete profile`/`;unlink profile` require picking which identity (by number or id) whenever you own more than one, listing them first rather than guessing -- a safety net against either command accidentally landing on the wrong one.

## Multi-bridge rooms

A single Matrix room can be a Matrix, ActivityPub, Bluesky (atproto), and Nostr identity all at once -- the same room bridged separately by each protocol's own bridge, each running as its own AppService against the same homeserver.

- **Ghost/bot namespacing** already works out of the box as long as each bridge configures a distinct `appservice.user_prefix`/`bot_localpart` (the defaults, `ap_`/`bridgebot`, are this bridge's own; a sibling bridge needs its own, different ones) -- there's no other identity-namespacing mechanism to worry about.
- **Command prefix collisions**: `;` is this bridge's own default specifically because it's short and, in practice, rare as a bot prefix (unlike `!`/`.`, both extremely common defaults for other Matrix bots/bridges) -- but it's configurable (`bridge.command_prefix`, see [CONFIG.md](CONFIG.md#bridge-command_prefix)) if it ever collides with something else in a shared room.
- **Other bridges'/bots' own commands never get federated as posts**: list their prefix(es) in `bridge.other_bot_prefixes` (see [CONFIG.md](CONFIG.md#bridge-other_bot_prefixes)) -- without this, a message meant as a command for a DIFFERENT bridge would fall straight through this bridge's own "not one of my commands" check (since it has no way to recognize another bot's own keyword vocabulary) and get posted to the fediverse as if it were ordinary content. This bridge still correctly never treats that message as addressed to its OWN bot either -- no reply, no attempted command parsing, it's simply excluded from federation. A short prefix (`!`, `nostr:`, ...) only counts at the very start of a message; a full mxid (another bridge's own bot, e.g. `@bluesky:yourdomain`) counts as a real mention of it anywhere -- a proper intentional mention OR the literal mxid typed in the body, since a client's own plain-text fallback for a mention pill is usually that bot's display name, not its mxid.
- **Other bridges' ghosts never get mistaken for confused local Matrix users**: list their mxid pattern(s) as regexes in `bridge.other_bridge_users` (see [CONFIG.md](CONFIG.md#bridge-other_bridge_users)) -- e.g. `@bsky_.*:yourdomain` for a Bluesky bridge's ghosts. A sibling bridge's ghost mirroring a reply, reaction, or vote into a room this bridge also tracks has no linked profile here (it's a puppet account, not a real human) -- without this, this bridge would try to resolve one anyway, fail, and send a "link a profile first" notice into the shared room every single time, which that ghost obviously can never act on. This is a different problem from `bridge.other_bot_prefixes` above: that one recognizes another bridge's *commands*; this one recognizes another bridge's *ghosts*.
- **The bridge widget, MSC2346 bridge-info state events, and MSC4501 profile-room tagging all already coexist safely** with a sibling bridge doing the same: the widget uses a fresh random state key per add (several bridges' widgets just become separate entries in the same room), `m.bridge` state events are keyed by protocol scheme (`activitypub://...`, leaving room for a sibling bridge's own `atproto://...`/`nostr://...`), and `m.social.profile_user_id` is a protocol-agnostic MSC4501 fact (multiple bridges asserting the same true thing about the same room is the correct outcome, not a collision).
- **Only one bridge should ever create a given room.** A sibling bridge attaching to an EXISTING room (the way `;link profile` lets this bridge attach to a room it didn't create) is the right way to add a second protocol to a room that already has one -- each bridge insisting on creating its own fresh room defeats the whole point of sharing one.
- **Reposting or replying to a sibling bridge's own content** (🔁-reacting to, or `;repost`ing, a Bluesky/Nostr post mirrored in as a ghost's message; replying to one) sends a real, standalone ActivityPub post quoting it -- text, a working link back to the original (the real public permalink both sibling bridges already stamp as `external_url` on everything they mirror in, not just this bridge's own `ap_object_id`), and attribution, read from that same MSC4503 `external_handle` metadata this bridge uses for its own ghosts. Never a real `Announce`/boost, since there's no foreign ActivityPub object to boost -- a plain `Create<Note>` instead, same as an ordinary post (redacting it later sends a real `Delete`, same as any other post). Without this, reposting/replying to a sibling bridge's content silently did nothing (🔁) or published a decontextualized fresh post with no quote at all (a reply).
- **This bridge's own repost cards carry `external_url` too**, for the same reason in reverse: a sibling bridge mirroring an AP-side repost back out to its own network needs a real link to the original, not just this bridge's internal bookkeeping.
- **`;link profile` never overwrites an already-set room name/avatar** (e.g. one a sibling bridge already branded the shared room with) -- same "preserve what's already there" treatment this already gave the room's topic/bio. Only fills in a still-blank name/avatar from the sender's own Matrix profile, exactly as before.

## PeerTube video channels

Opt-in (`bridge.peertube_channels_enabled`, off by default -- every remote view/scrub of a hosted video streams through the bridge's own media proxy with no caching layer, a real bandwidth cost to weigh first).

- **Publishing**: `;create channel <id>` turns a Matrix room into a real, federating PeerTube-compatible video channel -- a `Group`-typed ActivityPub actor with its own keypair, owned by an already-linked Profile (if you own more than one identity, say which with `as <number|id>` -- see [Multi-identity support](#multi-identity-support)). Reply to an uploaded video with `;publish` (`key: value` metadata lines -- name/category/license/language/tags/sensitive/commentsEnabled -- then a blank line and description) to federate it as a real PeerTube `Video`, delivered as `Create` to the owner's own followers and `Announce` to the channel's, matching PeerTube's own publish choreography.
- `;edit` changes a published video's metadata without touching the file. `;replace video` swaps the underlying file while keeping the same video identity. `;unpublish` retracts it from the fediverse; the Matrix message itself is untouched, so it can be re-published later.
- A video's reactions support a real `Dislike` (👎) alongside the usual `Like`/`EmojiReact`, and inbound `View` activities from remote instances are tallied into a durable view count. Comments (Matrix thread replies) federate as `Note`s the same way an ordinary post's replies do, and incoming comment content renders Markdown, PeerTube's own convention there.
- Playback goes through the bridge's media proxy with extension-aware URLs and CORS preflight handling, so a remote video player can actually infer a playable file type and stream byte-range requests.
- **Following**: `;follow` a remote PeerTube channel or account exactly like any other fediverse actor -- its videos show up as posts in your Remote User Room the same way an ordinary account's Notes do, and `;backfill` pulls its history in the same way too. Whether a followed video is downloaded and re-hosted natively or just linked back to its original instance as a card is controlled by `bridge.follow_video_media_mode` (`"link"`/`"embed"`, default `"link"`, falling back to a link card when the file is bigger than `bridge.follow_video_max_embed_mb`).

## Guilds and channels (Shoot)

- `;joinguild CODE@guild.example.com` joins a Shoot guild (an `Organization` actor) using an invite code, per FEP-bebd. The guild's `Accept` arrives later over the inbox, so this only sends and records the join request rather than confirming membership immediately.
- A joined guild gets its own Matrix Space, with each of its text channels mirrored into a child Matrix room -- immediately for a channel already known when the guild was joined, or the first time anyone posts in a newer one otherwise.
- Channel messages mirror bidirectionally: an incoming channel message is attributed to whichever guild member actually wrote it (never the channel actor itself), and an outgoing Matrix message sent in a channel room federates back out the same way.
- `;leaveguild`, run inside one of that guild's own channel rooms, sends a real `Undo(Follow)` and drops the bridge's own local membership tracking.
- `;refresh guild` re-syncs a guild's channel list by hand -- Shoot doesn't federate channel-creation events at all, so a channel created after the guild was joined is otherwise only discovered once someone actually posts in it.
- `;refresh guild invite CODE@domain` (admin-only) stores an invite code on the guild's own Space. From then on, a local Matrix user who joins that Space or any of its Channel rooms is automatically joined to the guild over ActivityPub too, with no `;joinguild` needed -- an unlinked user is DMed to link a profile first instead of silently failing, and a failed auto-join (bad/expired code, unreachable guild) is DMed rather than dropped. Running it also immediately resyncs any current Space member who's missing a real accepted Follow, covering both a stale code being replaced and anyone who joined before a code was ever set.

## Lemmy communities

A hosted or mirrored community's activity shapes match real Lemmy's own wire format (confirmed against captured Lemmy outbox/post/community JSON) and have been verified live against a real Lemmy instance: resolve, subscribe, posting, and comments all work correctly in both directions.

### Cross-platform attribution quirk

A community's own posts only show up consistently as *coming from the community* on another Lemmy instance (or another matrix-appservice-activitypub bridge) -- on Mastodon/Pleroma/Akkoma the content itself federates fine but renders under the original poster's account instead, and on Misskey/Sharkey it shows up as a boost on the community's "All" tab rather than a first-class post. This is a limitation of those platforms' own Group-actor handling, not something fixable by changing what this bridge sends.

### Mirroring a remote community

Opt-in (`bridge.lemmy_communities_enabled`, off by default -- same "real, substantial behavior change" reasoning as PeerTube channels).

- `;follow` a Lemmy community (a `Group` actor with its own moderators collection, named via its own `attributedTo` field -- detected via NodeInfo or the actor document) like any other fediverse actor, or paste a community link (`.../c/name`) directly -- it gets a shared `org.matrix.msc4501.social.group` Matrix room, not a 1:1 Remote User Room, since many different Lemmy users post and comment in it. Each poster/commenter shows up as their own ghost, resolved per-post/comment, same mechanism as a joined Shoot guild channel.
- A real Lemmy moderator of the community is mapped to Matrix power level 50 in the room. A local Matrix user who IS a genuine remote mod can exercise real moderation power from Matrix: banning a ghost sends a signed `Block` to the community, and redacting someone else's post/comment sends a signed `Delete` (as the mod, not the original author) -- Synapse's own power-level enforcement is what verifies the sender's authority before either ever reaches this bridge. A plain Matrix kick has no Lemmy equivalent and stays Matrix-only.
- Replying to a mirrored post or comment federates out as a real `Create<Note>` addressed directly to the community; starting a brand new top-level post from Matrix isn't supported for a MIRRORED community (see hosting below for one this bridge owns, where it is).
- The community's own first-ever follow on this server triggers a one-time auto-backfill of its latest posts, same as an ordinary followed account. `;backfill [N]` also works by hand afterward -- bare, it pulls the community's outbox (unwrapping its `Announce<Create<Page>>` fan-out shape); run as a reply inside a mirrored post/comment's own thread, it pulls that specific thread's comments instead (with the same Mastodon-API discovery fallback for an under-reporting `replies` collection that an ordinary account's thread backfill already has).
- `;refresh`, run bare inside a mirrored community room, resyncs its name/topic/avatar and moderator list immediately. The same resync also runs (debounced, `bridge.lemmy_community_resync_min_interval_seconds`) on an inbound profile `Update` and on any moderator Add/Remove, and is always serialized per-room so two triggers never resync concurrently.

### Hosting your own community

Opt-in separately (`bridge.lemmy_community_hosting_enabled`, off by default) -- hosting means this bridge is the authoritative home instance for the community, a real responsibility mirroring never has: it must accept posts/comments from anyone (local or remote) and re-`Announce` them to its own followers itself, since nobody else does that for it.

- `;create community <id> [as <number|id>] [name]` mints one from scratch (say which identity moderates it with `as <number|id>` if you own more than one -- see [Multi-identity support](#multi-identity-support)); `;link community <id>` turns an already-existing room into one instead. See [Commands](COMMANDS.md#lemmy-communities) for both.
- A Matrix member with a linked profile posts by just sending a message (first line = title, blank line, then the body) or replying to add a comment -- federates as a real `Create<Page>`/`Create<Note>` (signed by the poster) plus an `Announce` (signed by the community) to its followers, the same Create+Announce choreography `;publish` already uses for a PeerTube channel.
- A post/comment arriving from a remote fediverse user addressed directly to the community (never Announce-wrapped -- nobody else announces for it) is imported the same way, then re-`Announce`d to the community's own followers, excluding whoever originally sent it.
- The room's own name/topic/avatar/banner map onto the community's actor document, pushed out as a signed `Update` to followers on every change (reusing PeerTube channels' own `push_channel_update`-style mechanism). `;refresh`, run bare inside the room, re-broadcasts the current state on demand (there's nothing remote to pull from -- this bridge already IS the source).
- A community has no single owner (`;create community`'s sender becomes its first moderator, nothing more) -- raising anyone's Matrix power level to 50+ in the room makes them a REAL moderator (persisted, and announced to followers via a signed `Add`), unlike the mirrored direction, which can only ever reflect someone else's real list. Banning/redacting works the same way mirroring does, just broadcast to the community's own followers instead of delivered to a single remote inbox.

## Discovery and federation plumbing

- **HTTP Signatures** on every outbound activity and every inbound delivery, including cross-checking the signing key's actor against the activity's own claimed actor to reject spoofing.
- **WebFinger**, both serving local identities for remote discovery and resolving remote handles for outgoing follows, mentions, and DMs.
- **NodeInfo** (`/.well-known/nodeinfo`, `/nodeinfo/2.0`, `/nodeinfo/2.1`), the standard discovery document directory/crawler sites (fedidb.com, fedilist.com, the-federation.info) check before listing a domain as a federated instance at all.
- A minimal **Mastodon-compatible instance API** (`/api/v1/instance`, `/api/v1/instance/peers`), read by the same crawler sites; `contact_account` is configurable via `bridge.instance_admin_username`. Nothing else in the Mastodon API is implemented.
- **Outbox/followers/following/actor pages** are all served live, reconstructed from actual Matrix room state and history on every request, never cached separately, in keeping with the project's philosophy that Matrix is the only place content lives.
- **Rich link previews**: a plain browser (or a URL-preview scraper, like the one behind Element's own message link previews) landing on a profile or post permalink (`/actor/{username}`, `/actor/{username}/notes/{id}`) gets OpenGraph/Twitter Card meta tags -- title, a plain-text description, and an image (the post's own attachment if it has one, falling back to the author's avatar) -- so pasting one of this bridge's own links into a Matrix room shows the same kind of rich card a sibling bridge's own links (e.g. a `bsky.app` post link) already do, instead of a bare blue link.
- A **shared inbox** endpoint, plus per-actor inboxes, both signature-verified.
- **Knock-based self-service room access**: every bridge room uses Matrix's `knock` join rule, and a knock from that room's rightful local owner (current or a past, since-replaced room) is auto-accepted without side effects.
- **Optional peeking on Remote User Rooms** (`bridge.world_readable_remote_rooms`, off by default): sets `history_visibility: world_readable` so anyone on this homeserver can preview a Remote User Room's content -- including a followed PeerTube channel's, which uses the same room type -- without joining or knocking first, e.g. to independently verify a repost's own `social.relates_to` block against its actual claimed source rather than trusting it outright. `;refresh` run inside one of these rooms re-syncs it to match the current setting either way, not just at room creation.

For the exact ActivityPub activity types, Matrix event shapes, and implementation entry points behind each of these, see the source: `bridge/inbox_dispatch.py` for incoming, `bridge/note_mirroring.py`/`bridge/reply_bridge.py`/`bridge/reaction_bridge.py`/`bridge/edit_bridge.py`/`bridge/chat_bridge.py` for outgoing, `bridge/activitypub/routes.py` for the ActivityPub HTTP surface the bridge itself serves, `bridge/peertube.py`/`bridge/commands.py` for video channels, and `bridge/channel_bridge.py`/`bridge/spaces.py` for Shoot guilds and channels.
